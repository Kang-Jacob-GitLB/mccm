## 먼저: 이 그림들이 개발자용과 다른 점

개발자용 다이어그램은 **구조**를 그린다. 무엇이 무엇을 부르는지, 데이터가 어디로 흐르는지. 읽는 사람이 그 표기법을 배웠다는 전제 위에 서 있다.

비개발 독자에게는 그 전제가 없다. 그래서 여기 그림들은 전부 **사람이 겪는 일**을 그린다. 같은 시스템을 그리더라도 축이 다르다.

| | 개발자용 | 비개발자용 |
|---|---|---|
| 박스가 뜻하는 것 | 모듈·서비스·클래스 | 사람이 하는 일, 또는 사람이 보는 결과 |
| 화살표가 뜻하는 것 | 호출·의존 | "그다음에 무슨 일이 일어나는가" |
| 좋은 라벨 | 함수·프로토콜 이름 | 동사구 — "주문서를 넘긴다" |
| 지워도 되는 것 | 없음 (정확성) | 결론이 안 바뀌는 모든 것 |

**세 가지를 늘 지킨다.**

1. **화살표에는 반드시 동사가 붙는다.** 라벨 없는 화살표는 "관련이 있음"이라는 뜻인데, 그건 정보가 아니다.
2. **사람이 하는 일과 저절로 되는 일을 시각적으로 구분한다.** 비개발 독자가 가장 알고 싶어하는 것이 대개 이것이다 — "그래서 내가 뭘 해야 하나."
3. **한 그림에 강조색은 하나.** 색이 곧 "여기를 보라"는 신호다. 두 곳을 강조하면 신호가 사라진다.

## 은유 고르기

절차는 셋이다.

**① 독자가 매일 하는 일의 목록을 떠올린다.** 결재 올리기, 재고 확인, 견적서 작성, 입고 검사, 일정 조율, 고객 응대, 예산 배정, 출입 통제.

**② 설명할 것의 **관계 구조**와 같은 모양을 찾는다.** 표면이 비슷한 것이 아니라 **관계가 같은 것**을 찾아야 한다. "여러 요청이 몰리면 하나씩 처리하느라 뒤에 밀린다"의 짝은 "창고 출고 대기줄"이지 "창고"가 아니다.

**③ 밀고 나가서 어긋나는 지점을 찾는다.** 은유로 세 문장쯤 설명해 보고, 원래 것과 결론이 갈리는 지점을 미리 안다. 그 지점 **앞까지만** 쓴다.

### 잘 붙는 짝

| 설명할 것 | 은유 | 왜 맞는가 |
|---|---|---|
| 요청이 몰려 처리가 밀린다 | 출고 대기줄 | 도착 속도 > 처리 속도면 줄이 길어진다 — 관계가 같다 |
| 미리 만들어 둬서 빠르다 | 완제품 재고 | 미리 만들면 빠르지만 안 팔리면 버린다 — 대가까지 같다 |
| 나중에 갚아야 할 부실한 구현 | 외상 | 지금 빠르고 나중에 이자가 붙는다 |
| 바꾸면 다른 데가 깨진다 | 조립 라인 규격 변경 | 앞뒤 공정이 다 맞춰져 있다 |
| 검증 절차를 자동화했다 | 입고 검사 자동화 | 사람이 하던 확인을 기계가 한다, 놓치는 것도 달라진다 |
| 한 곳이 멈추면 전체가 멈춘다 | 단일 통관 창구 | 대체 경로가 없다는 점이 핵심 |

### 어긋나는 은유의 신호

- 은유를 설명하는 데 두 문장 이상 든다 → 독자가 그 은유를 모른다
- 은유 쪽에서는 당연한 해결책이 원래 것에서는 안 된다 → **가장 위험한 종류.** 독자가 "그럼 그냥 사람 더 뽑으면 되잖아"라고 결론 내린다
- 그림마다 은유가 조금씩 바뀐다 → 하나로 못 버티는 것이니 은유를 접고 직접 그린다

## 색 규약

의미가 있는 곳에만 색을 준다. 나머지는 전부 `currentColor`.

```css
:root {
  --bf-focus:   #1d4ed8;   /* 지금 봐야 할 곳. 그림당 한 군데 */
  --bf-next:    #15803d;   /* 앞으로 달라지는 것 */
  --bf-trouble: #b91c1c;   /* 막힌 곳, 문제 지점 */
  --bf-manual:  #a16207;   /* 사람이 직접 하는 일 */
}
:root:not([data-theme="light"]) {
  @media (prefers-color-scheme: dark) {
    --bf-focus: #60a5fa; --bf-next: #4ade80;
    --bf-trouble: #f87171; --bf-manual: #fbbf24;
  }
}
:root[data-theme="dark"] {
  --bf-focus: #60a5fa; --bf-next: #4ade80;
  --bf-trouble: #f87171; --bf-manual: #fbbf24;
}
```

인라인 SVG는 페이지의 CSS 변수를 상속받으므로 `fill="var(--bf-focus)"`로 참조하면 테마 전환이 저절로 따라온다. `artifact-design`이 정한 팔레트와 어긋나면 그쪽 색조를 따르되, **네 색이 서로 구별되고 양쪽 테마에서 읽히는 것**만 지킨다.

**색만으로 뜻을 전달하지 않는다.** 색맹 독자와 흑백 인쇄를 생각하면, 색이 하는 말은 라벨이나 모양이 한 번 더 해야 한다.

## 공통 치수

| 요소 | 값 |
|---|---|
| `viewBox` 폭 | **`190 × 단계 수`** (2단계 380, 3단계 570, 4단계 760) |
| 단계 박스 | `w=150 h=56 rx=8`, 좌여백 20에서 시작 |
| 단계 간 가로 간격 | 40 (좌표 간격 190) |
| 사람 표시 원 | `r=16`, 박스 위 중앙에 겹쳐 배치 |
| 본문 텍스트 | `font-size=13`, 박스 안은 `text-anchor="middle"` |
| 화살표 라벨 | `font-size=12`, `opacity=.85`, **박스 위** `y = 박스y − 8` |
| 캡션(`figcaption`) | SVG 밖. 그림 안에 설명 문장을 넣지 않는다 |

박스 안 한 줄 텍스트의 세로 중심은 `y = 박스y + 33`, 두 줄이면 `박스y + 25`와 `박스y + 42`.

**폭을 고정값으로 잡지 마라.** `190 × 단계 수`는 좌우 여백 20을 포함한 값이다(`20 + 190(n−1) + 150 + 20`). 720으로 고정하면 3단계까지만 들어가고 4번째 박스는 오른쪽 끝이 740이 되어 **오류 없이 그냥 사라진다.**

**화살표 라벨을 선 위에 두지 마라.** 간격이 40뿐이라 12px 라벨은 3.3자를 넘는 순간 양옆 박스 테두리를 파고든다. 한국어 동사구는 3자가 사실상 하한이므로, 「화살표에 반드시 동사」 규칙을 지키는 한 선 위에는 자리가 없다. 박스 위(`박스y − 8`)로 올리면 라벨 12자까지 안전하다 — 그 높이에서는 이웃한 사람 표시 원과 x로 갈린다.

**단계는 4개를 넘기지 않는다.** 넘으면 묶어서 줄인다 — 5단계면 폭이 950이 되어 본문 폭에 맞추느라 13px 글자가 10px 아래로 눌린다.

## 여정 그림

가장 자주 쓰게 되는 그림이다. 사람이 무엇을 하면 무엇이 일어나는지를 왼쪽에서 오른쪽으로 따라간다.

**사람이 하는 일과 저절로 되는 일을 반드시 구분한다.**

- 사람이 하는 단계 — 박스 위에 사람 원(`--bf-manual` 채움) + 테두리 `--bf-manual`
- 저절로 되는 단계 — 테두리만 `currentColor`, `opacity .75`
- 기다림이 있는 구간 — 화살표 아래에 시간 라벨 ("보통 2~3일")

```html
<figure>
  <svg viewBox="0 0 380 150" role="img" style="max-width:100%; height:auto"
       aria-label="주문서를 넣으면 재고 확인으로 넘어가는 흐름">
    <defs>
      <marker id="bf-ar" viewBox="0 0 10 10" refX="9" refY="5"
              markerWidth="6" markerHeight="6" orient="auto-start-reverse">
        <path d="M0,0 L10,5 L0,10 z" fill="currentColor"/>
      </marker>
      <!-- 색 있는 선에는 같은 색 마커를 따로 쓴다. 마커 안의 currentColor 는
           참조하는 선이 아니라 마커 자신의 상속 경로에서 색을 받기 때문이다 -->
      <marker id="bf-ar-focus" viewBox="0 0 10 10" refX="9" refY="5"
              markerWidth="6" markerHeight="6" orient="auto-start-reverse">
        <path d="M0,0 L10,5 L0,10 z" fill="var(--bf-focus)"/>
      </marker>
    </defs>

    <!-- 1단계: 사람이 하는 일 -->
    <rect x="20" y="50" width="150" height="56" rx="8"
          fill="none" stroke="var(--bf-manual)" stroke-width="1.5"/>
    <circle cx="95" cy="50" r="16" fill="var(--bf-manual)"/>
    <text x="95" y="83" text-anchor="middle" font-size="13">주문서를 넣는다</text>

    <!-- 화살표 + 동사 라벨. 라벨은 선 위가 아니라 박스 위(50 − 8 = 42) -->
    <line x1="176" y1="78" x2="204" y2="78" stroke="currentColor"
          stroke-width="1.5" marker-end="url(#bf-ar)"/>
    <text x="190" y="42" text-anchor="middle" font-size="12" opacity=".85">넘어간다</text>

    <!-- 2단계: 저절로 되는 일 -->
    <rect x="210" y="50" width="150" height="56" rx="8"
          fill="none" stroke="currentColor" stroke-width="1.5" opacity=".75"/>
    <text x="285" y="83" text-anchor="middle" font-size="13">재고를 확인한다</text>
  </svg>
  <figcaption>주문서를 넣으면 재고 확인까지 사람 손이 한 번만 든다.</figcaption>
</figure>
```

캡션은 장식이 아니라 **그림이 말하는 결론**이다. "주문 처리 흐름" 같은 제목을 달면 캡션이 일을 안 한 것이다.

**시스템 내부를 단계로 세우지 않는다.** "요청을 검증한다 → 데이터를 저장한다"는 사람에게 안 보이는 일이라 여정이 아니다. 사람에게 보이는 것만 단계가 된다.

## 두 장면 대비

「지금」과 「앞으로」를 위아래로 쌓는다. 좌우로 나란히 놓으면 각 패널이 절반 폭으로 눌려 단계 세 개도 안 들어간다.

- **같은 좌표계를 쓴다.** 안 바뀐 단계는 두 패널에서 정확히 같은 x에 둔다. 자리가 같아야 눈이 차이만 집어낸다.
- 왼쪽 여백에 패널 이름 (`지금` / `앞으로`, `font-size=13 font-weight=600`)
- **바뀐 것에만 `--bf-next`.** 나머지는 `currentColor`
- 없어지는 단계는 아래 패널에서 점선 + `opacity .3`으로 자리에 남긴다. 자리를 비우면 무엇이 사라졌는지 안 보인다
- **구조가 아니라 경험의 차이를 그린다.** 사람이 겪는 것이 안 바뀌었다면 그릴 그림이 아니다 — 그건 개발자에게만 의미 있는 변경이니 글 한 줄로 족하다

캡션에 결론을 쓴다: "확인 전화를 기다리는 이틀이 없어진다."

## 크기 비교

숫자를 글로만 쓰면 크기가 느껴지지 않는다. "1,200건"과 "80건"의 차이는 막대 두 개면 즉시 보인다.

- **막대는 반드시 0에서 시작한다.** 잘라 쓰면 비율이 왜곡되고, 이건 왜곡 중에서도 가장 들키기 쉬운 종류다
- 가로 막대로 그린다 — 항목 이름이 한글이라 세로 막대에서는 라벨이 눕는다
- 막대 끝 바깥에 숫자를 쓴다 (`text-anchor="start"`, `x = 막대끝 + 8`)
- 비교 대상은 **2~4개.** 그 이상은 표가 낫다
- 항목이 20개 이하이고 "건수"가 직관적이면 아이콘 반복도 좋다 — 다만 **한 아이콘이 몇 건인지 범례에 쓴다**

막대 폭 = `(값 / 최댓값) × 420`, 막대 높이 28, 간격 16. 좌표는 항목 이름 `x=20`(`text-anchor="start"`), 막대 시작 `x=200`(가장 긴 막대의 끝이 620), 숫자 `x = 막대끝 + 8`. `viewBox`는 폭 720, 높이는 `항목 수 × 44 + 24`. 이 그림은 단계가 없으므로 폭이 720으로 고정이다.

숫자 여러 벌을 본격적으로 시각화한다면 `dataviz` 스킬을 읽고 그 규약을 따른다.

## 갈림길

선택지를 놓고 결정을 받아야 할 때 쓴다.

- 분기점은 왼쪽에 작은 원 하나. 거기서 2~3갈래가 오른쪽으로 벌어진다
- 각 갈래 **선 위에 조건**, 갈래 **끝 박스에 결과**
- 결과 박스 아래에 **얻는 것 / 잃는 것** 두 줄 (`font-size=12`, baseline 간격 16 이상)
- 권고안이 있으면 그 갈래만 `--bf-focus` + `stroke-width=2`. 나머지는 `currentColor`
- **권고 이유는 그림이 아니라 캡션에 쓴다.** 그림은 선택지를 보여주고, 판단 근거는 글이 진다

갈래가 4개를 넘으면 축이 둘인 것이니 표로 바꾼다.

## 영역 그림

"어디까지가 우리 몫인가"를 그린다. 범위 협의·책임 분담에서 화살표 그림보다 훨씬 잘 듣는다.

- 큰 사각형 안에 작은 사각형을 넣는 **포함 관계**로 그린다. 화살표는 쓰지 않는다
- 우리 몫은 옅게 채우고(`fill="var(--bf-focus)" fill-opacity=".12"`) 테두리 `--bf-focus`. 남의 몫은 테두리만 `currentColor` + 파선
- **`opacity`가 아니라 `fill-opacity`다.** `opacity`는 채움과 테두리를 합성한 뒤 요소 전체에 걸려 테두리까지 12%로 지운다. 그러면 우리 몫과 남의 몫을 가르는 유일한 신호가 죽고, 불투명 파선인 남의 몫이 오히려 더 진해진다
- 각 영역의 이름은 **왼쪽 위 안쪽**에 (`text-anchor="start"`, `x = 영역x + 12`, `y = 영역y + 20`)
- 겹치는 영역이 있으면 그 자체가 협의해야 할 지점이니 겹쳐 그리고 캡션에서 짚는다

중첩은 3겹까지. 그 이상은 독자가 경계를 못 센다.

## 끊어진 지점

장애·병목을 설명할 때 쓴다.

- 정상 경로를 먼저 **전부** 그린다 (`currentColor`, `opacity .5`)
- 끊긴 곳 **하나만** `--bf-trouble`로 표시한다. 선을 끊고 그 자리에 X 표(두 선분 교차, `stroke-width=2.5`)
- 끊긴 지점 아래에 무슨 일이 일어나는지 한 마디 ("여기서 멈춰 뒤가 다 밀린다")
- 뒤에서 밀리는 부분은 `opacity .3`으로 흐리게 — 영향 범위가 그림으로 보인다

**끊긴 곳을 두 군데 이상 표시하지 않는다.** 원인이 여럿이면 가장 먼저 풀 것 하나만 그리고 나머지는 글로 쓴다.

## 한글 치수와 겹침

한글은 라틴 문자와 치수가 크게 달라서 **영문 감각으로 잡은 간격이 한글에서는 그대로 겹침이 된다.** 계산 규칙과 좌표 검산 절차는 같은 플러그인 `report` 스킬의 `references/diagram-recipes.md` 「한글 텍스트 치수」·「겹침 방지」 절에 정리돼 있다 (`../../report/references/diagram-recipes.md`). 그림을 그리기 전에 그 두 절을 읽는다.

여기서 반복해 둘 만한 것은 셋이다.

- **한글 한 글자 폭 ≈ `font-size` × 1.0** (라틴 소문자는 0.55). 박스 안 텍스트 폭이 `박스 폭 − 24`를 넘으면 글자를 줄이거나 박스를 넓힌다
- **두 줄 라벨의 baseline 간격 ≥ `font-size` + 4**
- 좌표는 전부 파일에 숫자로 적혀 있으므로 **눈이 아니라 산술로 검산한다.** 폭을 넘긴 요소는 오류를 내지 않고 그냥 사라진다

## 흔한 실패

| 증상 | 원인 | 대응 |
|---|---|---|
| 그림은 예쁜데 무슨 말인지 모르겠다 | 화살표에 동사가 없다 | 모든 화살표에 "무엇을 한다"를 붙인다 |
| 독자가 "그래서 내가 뭘 해야 해?"라고 묻는다 | 사람이 하는 일이 구분돼 있지 않다 | 사람 표시를 넣고 색을 나눈다 |
| 그림이 많은데 하나도 안 남는다 | 강조색이 그림마다 여러 개 | 그림당 강조 한 군데로 줄인다 |
| 은유를 설명하는 데 문단이 든다 | 독자가 모르는 은유를 골랐다 | 독자의 직무에서 다시 고른다 |
| 독자가 엉뚱한 해결책을 제안한다 | 은유가 원래 것과 어긋난 지점까지 갔다 | 어긋나기 전에서 은유를 접는다 |
| 두 장면 대비가 비교되지 않는다 | 두 패널의 좌표가 다르다 | 안 바뀐 단계는 x를 똑같이 |
| 막대 차이가 실제보다 커 보인다 | 축을 0에서 시작하지 않았다 | 0에서 시작한다 |
| 다크 모드에서 그림이 사라진다 | 검정 하드코딩 | 안 강조한 요소는 전부 `currentColor` |
| 화살표 머리 색이 선과 다르다 | 마커를 하나만 정의해 재사용 | 색마다 마커를 따로 정의한다 (`bf-ar`, `bf-ar-focus`, `bf-ar-next`, `bf-ar-trouble`) |
| 좁은 화면에서 잘린다 | 고정 `width` 지정 | `viewBox` + `max-width:100%; height:auto` |
| 단계가 많아 눈이 미끄러진다 | 5단계 이상 | 묶어서 4개 이하로 |
| 마지막 단계가 통째로 안 보인다 | `viewBox` 폭을 720으로 고정했다 | 폭 = `190 × 단계 수` |
| 화살표 라벨이 박스 테두리를 파고든다 | 라벨을 선 위에 뒀다 (간격이 40뿐이다) | 박스 위 `박스y − 8`로 올린다 |
| 영역 그림에서 우리 몫 테두리가 흐리다 | `opacity`로 채움을 옅게 했다 | `fill-opacity`를 쓴다 |
